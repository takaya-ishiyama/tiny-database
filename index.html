何を学ぶか

完成品の機能数ではなく、各レイヤーで「なぜその設計が必要か」を説明できることを成功条件にする。 まず正しさを作り、壊し、観測し、それから速くする。

01

Bytes before SQL

SQLより先に、バイト列・ページ・ファイルの境界を扱う。DBの土台を見えなくしない。

02

Crash it on purpose

正常系だけで終えず、書き込み途中でプロセスを落とし、再起動後の状態を確かめる。

03

Measure, then optimize

I/O回数、キャッシュヒット率、木の高さを計測してから最適化する。勘だけで速くしない。

最初の境界線

最初からPostgreSQLを目指さない。最初の完成形は「単一プロセスで動く、永続化されたB+Tree型KVストア」。 深く学ぶために必要な難しさだけを残す。

Version 1 に入れる

  • Rustライブラリ + 対話型CLI
  • put / get / delete / scan
  • 4 KiB固定長ページとスロットページ
  • B+Treeインデックス
  • 小さなバッファプールとLRU系置換
  • WAL、チェックポイント、クラッシュリカバリ
  • 単純な排他制御とトランザクション

Version 1 ではやらない

  • ネットワークサーバーと認証
  • 分散合意、レプリケーション、シャーディング
  • 完全なSQL、JOIN、コストベース最適化
  • 本番レベルのMVCCと分離レベル一式
  • 圧縮、暗号化、オンラインバックアップ
  • OSごとの差を吸収する高度なI/O最適化

完成時の層

上から一気に作らず、下の層の不変条件をテストしてから次へ進む。各境界は小さなtraitで分離し、 テストではメモリ実装とファイル実装を差し替えられるようにする。

実装ロードマップ

期間は締切ではなく目安。各フェーズの「完了条件」が満たせなければ先へ進まない。 1フェーズごとに設計メモ、実装、テスト、振り返りを1セットにする。

00Week 1

観察できる土台を作る

2–3 sessions

ワークスペース、エラー型、テスト方針、用語集を先に置く。まだDBは作らない。

  • storage / index / transaction / cli のcrateまたはmoduleを作る
  • 単体・プロパティ・クラッシュテストの置き場を決める
  • バイトオーダー、ページサイズ、最大key/value長をADRに記録する
EXIT CRITERIA

cargo test と cargo clippy がCIで動き、設計上の未決事項が一覧化されている。

01Week 1–2

追記ログだけのKVストア

3–5 sessions

最短で永続化まで到達する。レコードを追記し、起動時にログを走査してメモリ上のindexを再構築する。

  • レコード形式: checksum / key length / value length / tombstone
  • put、get、delete と再起動テスト
  • 末尾が途中で切れたファイルを安全に無視する
EXIT CRITERIA

1万件を書き、プロセス再起動後も取得できる。途中で切れた最終レコードを検出できる。

02Week 3

Pagerとファイルフォーマット

3–4 sessions

ファイルを固定長ページの配列として扱う。DBヘッダー、ページID、free listを導入する。

  • read_page(id) / write_page(id) / allocate_page()
  • magic numberとformat versionで誤ったファイルを拒否する
  • 短いread/writeや境界外アクセスを明示的にエラー化する
EXIT CRITERIA

任意ページの書き込み・再読込が一致し、破損したヘッダーと不正なページIDを検出できる。

03Week 4

Slotted PageとHeap File

3–5 sessions

可変長レコードを固定長ページに詰める。slot directoryにより、レコード移動後もRIDを安定させる。

  • ページヘッダー、slot、free spaceのレイアウト
  • insert / read / delete / compact
  • ランダムな操作列に対するreference modelテスト
EXIT CRITERIA

追加と削除をランダムに繰り返しても、slotの重なりやページ境界越えが起きない。

04Week 5–7

B+Treeインデックス

6–9 sessions

最初はメモリ上、次にページ上へ移す。探索よりも、分割と親への伝播を丁寧に実装する。

  • leaf / internal node、separator key、sibling link
  • search / insert / split / range scan
  • deleteはまずtombstone、mergeとrebalanceは後から追加
  • 全leafが同じ深さ、key順、占有率などの不変条件検査
EXIT CRITERIA

ランダムな10万keyを挿入し、標準のBTreeMapと検索・範囲走査結果が一致する。

05Week 8

Buffer Pool

3–5 sessions

ページI/Oを直接呼ばず、有限個のframeを介する。pin、dirty、evictionの意味を体で理解する。

  • page table、frame、pin count、dirty bit
  • 単純LRUまたはClock置換
  • hit / miss / eviction / flushのメトリクス
EXIT CRITERIA

小さなframe数でもデータを失わず、pin中のページをevictしない。I/O削減量を数字で示せる。

06Week 9–10

WALとクラッシュリカバリ

5–7 sessions

「データページより先にログを永続化する」をコード上の制約にする。redo中心の小さな方式から始める。

  • LSN、page LSN、log record、commit record
  • write-ahead ruleと明示的なsync_all
  • checkpointと起動時redo
  • 任意の書き込み地点でkillするfault injection
EXIT CRITERIA

100箇所以上の強制終了パターンで、commit済みは残り、未commitは見えない状態へ復旧できる。

07Week 11

TransactionとConcurrency

4–6 sessions

まず1 writer / 複数readerの明快なモデルにする。その後、strict 2PLで競合とdeadlockを観察する。

  • begin / commit / rollbackとtransaction ID
  • shared / exclusive lock、lock table
  • deadlockはtimeoutから開始し、wait-for graphは発展課題
EXIT CRITERIA

dirty readとlost updateの再現テストが、導入した排他制御によって防止される。

08Week 12

使えるAPIとCLI

3–4 sessions

内部実装を隠す安定したAPIと、観察用コマンドを作る。SQLはここでもまだ必須ではない。

  • open / put / get / delete / scan / flush / stats
  • .pages、.btree、.walのinspection command
  • graceful shutdownと多重openの拒否
EXIT CRITERIA

新規DB作成から書き込み、再起動、範囲検索、統計確認までCLIだけでデモできる。

09Week 13–16

検証・計測・説明

finish line

ベンチマークの速さより、ボトルネックを説明できる状態を目指す。最後に設計を文章化する。

  • sequential / random、read-heavy / write-heavyのbenchmark
  • DBサイズ、B+Tree高さ、page read/write、cache hit rateを記録
  • ファイルフォーマット、リカバリ手順、既知の制約を文書化
  • append-only版とB+Tree版の比較レポート
EXIT CRITERIA

仕組み、選択理由、壊れ方、性能特性を図と数字で第三者へ説明できる。

1セッションの型

1回60〜120分を想定する。読むだけの日と実装だけの日を分離せず、小さな問いをコードで確かめる。

20 min · Read

問いを1つ決める

例: 「なぜslot directoryが必要か」。該当章を読み、実装前の予想を短く書く。

60 min · Build

最小単位で実装する

1つの不変条件だけを担当する差分にする。動作確認用のテストも同じ差分に含める。

15 min · Reflect

壊し、記録する

境界値や強制終了を試し、予想との差と次に調べることをnotes/へ残す。

テスト戦略

DBでは「一度通った」より「多様な操作列とクラッシュ後も不変条件を守った」が重要。機能ごとに検証方法を変える。

Reference model

既知の実装と比較

HashMapやBTreeMapへ同じ操作を流し、結果が一致するかを調べる。

Property test

操作列を生成

大量のinsert / delete / scanを自動生成し、木とページの不変条件を毎回検査する。

Fault injection

途中で落とす

I/O境界ごとに失敗を注入し、再起動後の状態がtransactionの約束を守るか確認する。

最初の設計判断

迷いを減らすための初期値。実装中に不都合を発見したら、理由をADRへ記録して変更する。

項目初期判断学べること
言語Rust stable所有権でページ参照やpinの寿命をどう表現するか。
利用形態Embedded + CLIネットワークを除外し、ストレージ内部へ集中できる。
データモデルVec<u8> key / value型システムやSQLより前の、物理表現に集中できる。
ページサイズ4 KiB固定長I/O、内部断片化、fan-outの関係を観察できる。
インデックスB+Treeページ局所性、木の高さ、範囲検索、分割を学べる。
耐久性WAL + redowrite ordering、fsync、commitの意味を明示できる。
同時実行Single writer → strict 2PL単純なモデルから競合、lock、deadlockへ進める。

伴走資料

最初から通読しない。実装フェーズに対応する章を必要になった時点で読み、コードで確かめる。
